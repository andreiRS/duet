# Duet v0.2 — Features & Improvements

Running list of ideas for the next version. Collected during v0.1 manual testing
plus a design study of the official Excalidraw MCP server
(`github.com/excalidraw/excalidraw-mcp`). Nothing here is committed work yet — it
is the backlog to slice from.

## Context

In v0.1 the agent edits a scene by reading, mutating, and writing the
`.excalidraw` JSON file directly (via ad-hoc `bun -e` scripts). The server
watches the file and live-syncs it to the browser. This works, but manual
testing surfaced clear gaps. The biggest one is that the agent has **no visual
feedback** — it writes coordinates by math and only the human sees the result.

## Highest-priority ideas

### 1. A single scene-edit core library (`resolveScene(base, ops) -> flat JSON`)
Today every agent edit is a bespoke `bun -e` script that hand-rolls element
shapes, positions, and the file envelope. Build one reusable core that owns:
load/parse, mutate, and atomic save. A CLI and an eventual MCP tool both wrap
the same core — no duplicated logic.

**Why:** the Excalidraw MCP server is the negative example here — it duplicates
its restore/delete/convert logic across server and client because it never
factored a core. We should not repeat that.

Proposed surface:
```
load(path)            -> retry-read past atomic swap
.byId(id) / .list()   -> query helpers (the MCP has NONE — we can do better)
.addBox / .addArrow   -> correct defaults, stable ids
.setLabel(id, text)   -> bound text, measured by Excalidraw, not by us
.centerX(els, x)       -> geometry helpers (bbox, midpoint)
.save({ source })     -> atomic write + correct scene envelope
```

### 2. Visual feedback loop — `duet snapshot <file> -> png/svg`
The agent has no eyes. A headless render the agent can read back (with the Read
tool) would let it self-correct layout before the human ever sees it. This is
the single capability that would have caught the "arrows stab through boxes"
mess in testing.

- Build on Excalidraw's `exportToSvg` / `exportToBlob` (the MCP uses these).
- Note: Playwright screenshots of the live canvas are unreliable in this setup —
  use a real headless export, not a canvas screenshot.

### 3. Bound arrows (edge-to-edge), not center-to-center
`authoring.ts` `arrow()` hard-codes `startBinding`/`endBinding` to `null`, so
arrows drawn between box centers plunge through the boxes and land arrowheads
inside them. Excalidraw binds arrows with
`{ elementId, fixedPoint:[fx,fy] }` (normalized: top `[0.5,0]`, right
`[1,0.5]`...) and then clips the arrow to the box border and reroutes on move.
Add real bindings to the authoring lib.

### 4. Bound labels + font-gated text measurement
Our naive width estimate (`length * fontSize * 0.55`, summed across all lines)
broke multi-line label centering — a label got a 1592px width. The MCP refuses
to measure multi-line text itself: it attaches a `label` to a container and lets
Excalidraw center + auto-resize. Two fixes:
- Prefer bound labels; reserve manual `x` math for single-line text only.
- Any geometry that depends on text size must wait for fonts:
  `await document.fonts.load(...)` first. Measuring before Excalifont loads
  corrupts dimensions.

### 4b. Agent-controlled camera (zoom-to-fit, pan, zoom)
There is no way today for the agent to control the viewport. The client applies
`appState` unfiltered through `updateScene` (`App.tsx:74`), so an agent *could*
set `scrollX/scrollY/zoom` from a file write, but zoom-to-fit needs the browser's
real viewport size — computing it server-side means guessing the window, the same
no-eyes problem as layout. Also `scroll*`/`zoom` are not in the write-back
whitelist (`writeback.ts:34`), so a set view never persists.

Wire it properly instead:
- Call `api.scrollToContent(elements, { fitToContent: true })` on apply so it
  fits exactly (Excalidraw computes zoom from the actual canvas size).
- Support **pan** and **zoom** too — express them as a `cameraUpdate`
  pseudo-element in the scene (the Excalidraw MCP does exactly this:
  `{ type:"cameraUpdate", x,y,width,height }`), so the agent can say "show this
  region" or "zoom to fit" as data, gated so it does not fight the human's manual
  pan/zoom on every edit.

## Echo guard / sync

### 5. Version-keyed echo guard
Current echo guard (commit `773f7fa`) uses a content hash. The MCP's
`edit-context.ts` is a tighter reference for browser->file write-back:
- Snapshot a stringified `id:version` map; bail immediately if unchanged.
- Debounce ~1-2s.
- Push the model a **compact diff** (`Added / Removed / Moved`), not the whole
  scene.

### 6. Keep ids stable across round-trips
The MCP uses `convertToExcalidrawElements(..., { regenerateIds: false })` so the
caller's ids survive — which is what makes delete-by-id and bindings work. If
our core wraps that conversion, keep ids stable and never reuse a deleted id.

## Agent ergonomics

### 7. Query / read tools (`read`, `list`, `get-by-id`)
The MCP has **no** read path for the model — it forces whole-scene resends. A
file-backed tool like Duet can do better: let the agent inspect elements and
mutate surgically instead of re-emitting everything.

### 8. CLI on top of the core (later)
Once the core exists, a thin `duet edit add-box / move / center / list` is cheap
and good for quick human tweaks. It is a convenience skin, not the agent's
primary interface — the agent should drive the core from short script files for
full flexibility.

### 9. MCP tool (later)
Most seamless for the agent (direct tool calls, no shell), but only worth it if
conversational editing gets heavy. Wraps the same core.

## Keep / do not regress

- **Atomic write** (temp-file + rename, commit `773f7fa`). The MCP's file store
  is plain `writeFile` — do not regress to that.
- **Source tagging** — browser writes `source:"duet"`, agent writes
  `source:"https://excalidraw.com"`; the client flashes on every applied scene
  after first load.
- **First-load buffer** (`pendingSceneRef`, commit `4e7c8ed`) — render existing
  file content immediately, suppress the flash on the initial load.

Noise test method: 40s file-hash monitor while generating mouse-move, hover,

scene-version advances; selection/pan/zoom live in appState and never bump it.

## Confirmed working in v0.1 testing (with gotchas)

### Dark mode — works via pure file write
Setting `appState.theme = "dark"` flips the canvas to dark with no code change
(the `<Excalidraw>` at `App.tsx:183` pins no `theme` prop, so it reads theme from
appState; `theme` is whitelisted in `writeback.ts:34`, so it round-trips).

**Gotcha:** dark theme applies an invert filter to the *whole* canvas
(`invert(93%) hue-rotate(180deg)`), including the background. So a "dark"
background must be stored as a **light** value (white -> near-black). A literal
dark hex gets inverted into light gray. If we add a `duet dark` helper or
agent-controlled theming, set `viewBackgroundColor` to white (or omit it) when
theme is dark, never a dark hex.

## Known bugs (found in v0.1 testing)

### B1. Human edits do not sync tab->tab live (only after refresh) — FIXED
Found in multi-tab testing: edit in tab A, tab B shows it only after a refresh.

**Fixed:** the `save` message handler now calls `ws.publish("scene", ...)` after a
successful write (`server.ts`). `ws.publish` excludes the sender, so tab A does not
bounce but tab B updates live. Echo guard / watcher path unchanged. Covered by test
"a browser save fans out to other connected clients but not the sender (B1)".

> **Superseded by ADR-0007 (#17).** The handler now re-reads + `mergeById`s the
> browser save against current on-disk state and broadcasts the **merged** scene
> to **all** tabs **including the sender** via `server.publish` (not `ws.publish`).
> Loop-prevention moved to the client's `isApplyingRemote` guard, not withholding
> the broadcast from the sender. The B1 test is now "broadcasts the merged scene to
> ALL tabs including the sender (B1, #17)". The fan-out described below still
> applies; only the sender-exclusion no longer does.

**Root cause:** when a browser `save` arrives, `server.ts` (message handler,
~L71-97) writes the file via `writeSceneFile(..., echoGuard)` — which registers
the bytes in the echo guard — updates `currentScene`, and **never broadcasts**.
The file-watcher then fires but `shouldSkip` -> `echoGuard.consume()` skips it.
So the echo guard, meant to stop the edit bouncing back to tab A, also swallows
the only path to tab B. Tab B catches up only via replay-on-connect
(`server.ts:69`), i.e. on refresh. Agent edits are unaffected (they go through
the watcher -> `setScene` -> `publish`).

**Fix:** in the message handler, after a successful write, fan out to other
clients with `ws.publish("scene", sceneMsg(currentScene))` — Bun's `ws.publish`
excludes the sender, so tab A still does not bounce/flash but tab B updates live.
Keep the echo guard as-is for the agent/file-watcher path. Add a test:
"a browser save fans out to other connected clients but not the sender."

### B2. Client can resurrect an agent hard-deleted element (no last-applied-remote baseline)
Follow-up from the ADR-0007 #18 review. `App.tsx` `applyScene` merges
`mergeById(remote, localCanvas)` and keeps every local-only id. With no baseline of
the last-applied remote scene, the client cannot tell an in-progress new element
(keep) from one that was deleted remotely (drop). If an agent **hard-deletes** an
element (removes it from the `open().list()` array → `reconcileForWrite` drops it
from disk → broadcast omits it), the client keeps it as local-only and it reappears.

**Latent, not active in v0.1:** there is no delete verb in `Verbs` (`authoring.ts`
only adds); the only trigger is an agent script splicing the live array directly.
Human-in-browser deletes are `isDeleted:true` tombstones (higher version) and are
handled correctly by the version tiebreak (see #18's `getSceneElementsIncludingDeleted`).

**Fix direction:** keep a `lastAppliedRemoteRef` in `App.tsx`; drop local-only ids
that were present in the previous remote but absent from the new one (remote
deletion), keep local-only ids never seen in any remote (genuine local add). This is
the client analog of the #16 write-path baseline diff.

### B3. Actively-drawn element can briefly revert on the #17 merged round-trip
Follow-up from the ADR-0007 #18 review. When the merged broadcast returns to the
sender, the in-progress element's shared id ties on `version` (server does not bump
on merge); `pickWinner` then falls to the versionNonce / canonical-JSON tiebreak,
which can pick the older remote copy over the fresher local one → a visible
jump/revert while the human is still drawing. Low-likelihood / timing-dependent.
**Fix direction:** prefer the client's own copy of the id currently being edited, or
add a higher-`updated`-timestamp tiebreak before the JSON fallback.

### B4. No test for an element surviving BOTH a forward and a reverse race in sequence
Each race direction is covered in isolation (`open.test.ts`, `server.test.ts`), but
nothing asserts end-to-end convergence across both write paths on the same shared
file (the ADR-0007 "residual race" accepted cost). Needs an agent-process + server
integration harness that does not exist yet — its own slice, not batch rework.

## Minor / cosmetic

### M1. Malformed-write warning prints a full stack trace
`watch.ts:73` does `console.warn(msg, err)`, so a `SyntaxError` from a bad scene
parse dumps a chokidar stack trace. For the malformed-scene case the message +
`err.message` is enough; the stack is noise. Log just the message there.

## Anti-patterns observed (avoid)

- Duplicating scene logic across server and client (the MCP does this).
- Shipping the element schema as a prose cheat-sheet string with no validation —
  prefer real (zod) schemas + a docs tool generated from them.
- Connecting a random/shuffled order of nodes — produces long crossing diagonals.
  Connect spatial neighbors.

## Appendix: how the agent edits today (the `bun -e` pain)

This is a verbatim example of an agent edit in v0.1 — it draws the
"how an agent edit reaches the screen" pipeline. Every edit looks like this: a
one-off `bun -e` script, cobbled inline, run from the shell. It is the workload
the scene-edit core (idea #1) and the snapshot loop (idea #2) exist to remove.

```sh
bun -e '
import { scene, PALETTE } from "./src/authoring.ts";
import fs from "fs";
const s = scene();
const P = PALETTE.light;

const BW=190, BH=96, Y=300, GAP=170;
// 4-stage pipeline, boxes laid out with fixed gaps so arrows fit in the empty gap.
const boxes=[
  {id:"agent", x:60,  fam:P.purple, label:"Agent"},
  {id:"file",  x:60+ (BW+GAP)*1, fam:P.amber,  label:"scene.excalidraw"},
  {id:"server",x:60+ (BW+GAP)*2, fam:P.blue,   label:"Duet server"},
  {id:"browser",x:60+(BW+GAP)*3, fam:P.green,  label:"Browser canvas"},
];
for(const b of boxes) s.labeledRect(b.id, b.x, Y, BW, BH, b.fam, b.label, 18);

// Arrows live ENTIRELY in the gap between consecutive boxes (no box-stabbing).
const midY = Y + BH/2;
const steps=["1. writes file","2. fs.watch fires","3. WS \"scene\" msg"];
for(let i=0;i<boxes.length-1;i++){
  const ax = boxes[i].x + BW;          // right edge of box i
  const bx = boxes[i+1].x;             // left edge of box i+1
  s.arrow("arr"+i, ax, midY, [[0,0],[bx-ax,0]], "#1e1e1e");
  // step label sits just ABOVE the arrow line, centered in the gap
  const t = steps[i];
  const tw = t.length*13*0.55;         // <-- naive width estimate (see idea #4)
  s.text("lbl"+i, Math.round((ax+bx)/2 - tw/2), midY-34, t, 13, "#495057");
}
s.text("title", 60, 150, "How an agent edit reaches your screen", 26);

const out = s.build();
out.source = "https://excalidraw.com";   // <-- hand-set envelope every time
fs.writeFileSync("scene.excalidraw", JSON.stringify(out,null,2)); // <-- not atomic from here
'
```

What is painful in this one snippet (each maps to an idea above):
- **No eyes.** Every coordinate (`x:60+(BW+GAP)*i`, `midY-34`) is guessed; the
  only check is the human looking at the screen. -> idea #2 (snapshot loop).
- **Manual gap-routing to avoid stabbing.** Arrows are hand-placed in the empty
  gap between boxes because there are no bindings. -> idea #3 (bound arrows).
- **Naive text width** (`t.length*13*0.55`) for centering — the same estimate
  that produced a 1592px label earlier. -> idea #4 (bound labels / real measure).
- **Envelope + persistence by hand** (`out.source = ...`, `JSON.stringify`,
  `writeFileSync`) — repeated and not atomic when written this way. -> idea #1
  (a `save({source})` that does the atomic write + envelope).
- **No query/read.** To *modify* an existing scene (e.g. the "center the two
  boxes" edit) the script re-reads the file, finds elements by id, and does the
  bbox math inline. -> idea #7 (`load`/`byId`/`centerX`).

Target for v0.2 — the same edit through the core library:

```ts
const s = load("scene.excalidraw");
const ids = s.pipeline(["Agent","scene.excalidraw","Duet server","Browser canvas"],
                       { labels:["1. writes file","2. fs.watch fires","3. WS \"scene\" msg"] });
s.fitView();                 // camera, computed from real canvas size
s.save({ source: "agent" }); // atomic write + envelope
await s.snapshot("/tmp/out.png");  // agent reads this back to self-check
```
